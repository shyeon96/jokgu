# 수정 순서와 검증 한계

아래는 [분석 항목](findings.md)을 바탕으로 정리한 제안입니다. 구현 완료나 승인된 마이그레이션 계획이 아닙니다. 이번 작업은 문서 작성만 수행했습니다.

## 1. 요청으로 수정할 수 있는 필드 제한

대상: C01, H04, L02, M09.

회원가입, 내 정보 수정, 경기장 등록에서 허용한 필드만 엔티티로 전달합니다. 기본키, 활성 상태, 비밀번호 등 서버가 별도 경로로 관리할 필드는 일반 요청 객체에서 받지 않습니다. DTO 런타임 검증도 함께 정리합니다. 전역 ValidationPipe만 켜는 것으로 끝내지 않고 각 DTO의 허용 필드와 검증 규칙을 정의해야 합니다.

완료 기준:

- 가입 요청에 기존 id를 추가해도 기존 계정과 비밀번호가 바뀌지 않습니다.
- 일반 프로필 수정으로 password, is_active 등 허용하지 않은 필드를 바꿀 수 없습니다.
- 경기장 등록 요청에 기존 id를 넣어도 기존 경기장이 바뀌지 않습니다.
- 잘못된 타입, 필수값 누락, 범위 밖 숫자는 저장 전에 일관된 4xx 응답을 받습니다.

## 2. 리소스별 권한과 입력 관계 검증

대상: C02, H01~H03, M05~M07, M10.

그룹 역할과 일정 소속을 서버에서 확인합니다. approve는 요청자 권한뿐 아니라 gid와 ugid가 같은 그룹을 가리키는지도 검증합니다. 일정 참가자, 양 팀, 심판이 허용된 범위에 있는지 확인합니다. 조회 API와 WebSocket에도 같은 정책이 필요합니다.

완료 기준:

- 비회원, pending, member, admin별 허용 동작을 먼저 문서로 확정합니다.
- 다른 그룹의 gid, ugid, pid, mid를 대입해도 비공개 조회나 변경이 되지 않습니다.
- 양 팀 중복 참가, 존재하지 않는 사용자, 일정 밖 참가자와 허용되지 않은 승자 값을 거부합니다.
- WebSocket의 join, updateScore, matchEnd도 역할과 대상 일정 권한을 확인합니다.
- 기록자 소유권이 없는 탭이 다른 기록자의 경기를 종료하지 못합니다.

## 3. 인증과 재설정 흐름 보완

대상: M01~M04, L01~L05.

재설정 권한과 일반 로그인 권한을 구분하고 코드 사용을 원자적으로 처리합니다. 사용자 식별 정책, 로그인 제한, 코드 발송 제한, 비밀번호 변경 뒤 토큰 무효화 정책을 정합니다. 탈퇴 API를 구현할 경우 기존 토큰의 처리와 그룹 관리자 탈퇴 규칙도 함께 정해야 합니다.

완료 기준:

- 로그인 JWT와 재설정 JWT를 서로의 용도로 사용할 수 없습니다.
- 이미 사용했거나 만료된 코드는 재사용할 수 없습니다. 동시 요청에서도 한 번만 성공합니다.
- 이메일 원문 노출과 사용자 존재 여부 안내 범위를 명시합니다.
- 발송 실패, 중복 이메일, 반복 로그인 요청의 동작을 정의하고 확인합니다.
- 탈퇴와 비밀번호 변경 후 HTTP/Socket 인증이 정한 정책대로 동작합니다.

## 4. 데이터 원자성과 날짜 계약 정리

대상: H05, M08, M17, L05~L07, L13, L17, L19.

먼저 실제 DDL, default, unique, FK, DB 세션 타임존을 확인합니다. 그룹과 관리자, 일정과 참가자, 경기와 팀별 결과를 각각 하나의 저장 단위로 묶습니다. 중복 방지는 UI 제출 잠금과 서버 측 중복 판정을 구분합니다. 날짜만 의미하는 값은 API에서 YYYY-MM-DD 형식을 유지하도록 계약을 정합니다.

완료 기준:

- 두 번째 저장을 강제로 실패시켜도 부모 행만 남지 않습니다.
- 동일 경기의 중복 요청이나 재시도가 정산을 두 번 반영하지 않습니다.
- 일정 삭제의 연관 행 처리가 확인된 FK 정책과 일치합니다.
- 같은 일정이 목록, 상세, 지난 일정에서 같은 날짜로 보입니다.
- DB와 앱의 시간 기준을 바꿔도 정한 기준의 오늘 일정과 5분 만료가 유지됩니다.
- SUM/COUNT 응답을 숫자로 정규화한 뒤 승률, 참여 비율, 금액을 계산합니다.

## 5. 화면과 실시간 점수 보완

대상: M11~M17, L09~L14.

경기장 응답 필드명을 맞추고 로그인 오류를 페이지 이동 없이 표시합니다. 점수 전환과 되돌리기의 방송을 빠짐없이 처리합니다. 실시간 캐시의 만료, 연결 단절, 기록자 재접속 정책을 정합니다. 현재 단일 프로세스 구조에서 해결할 수 있는 범위를 먼저 검토합니다.

완료 기준:

- 경기장 실제 값과 실내, 예약, 주차 표시가 일치합니다.
- 승리 점수의 빈 값과 범위 밖 값으로 경기가 자동 종료되지 않습니다.
- 득점, 세트 종료, 되돌리기, 경기 종료 후 기록자와 시청자 점수가 같습니다.
- 저장 직후 취소 토스트가 뜨지 않고 중복 저장 버튼이 잠깁니다.
- 잘못된 소켓 payload를 거부하며 시청 화면이 복구 불가능한 상태로 남지 않습니다.
- 조회 실패, 소켓 인증 실패, 지도 SDK 미로드를 빈 데이터와 구분합니다.
- 경기 종료 후 시청자 경기 목록과 정산도 새 결과를 반영하는지 확인합니다.

## 6. 재현 가능한 운영 기준 확보

대상: L15~L18, L20, L21.

실제 DB 스키마와 배포 설정을 문서화한 다음 필요한 migration과 실행 환경 고정을 검토합니다. 필수 env 검증, 현재 라우트에 맞는 e2e, 핵심 도메인 회귀 테스트, CI를 후속 구현 범위로 정합니다. 빈 모듈과 미사용 설정 정리, 폰트 최적화는 앞선 무결성 문제 이후에 검토합니다.

완료 기준은 새 환경에서 같은 스키마로 기동하고, 핵심 흐름의 검증 결과를 반복해서 얻는 것입니다. 빌드 통과만으로 권한, 데이터 무결성, 배포 성공을 판정하지 않습니다.

## 기존 분석에서 결함으로 확정하지 않은 항목

| 항목 | 확인 범위와 남은 한계 |
| --- | --- |
| SQL injection | 이전 분석은 raw SQL의 값 바인딩이 ? 플레이스홀더를 사용한다고 기록했습니다. 이번에 대조한 repository도 같은 방식입니다. 모든 입력 경로의 보안 보증은 아닙니다. |
| XSS | 이전 분석은 위험한 HTML 삽입 지점을 찾지 못했고 React의 href 처리도 확인했다고 기록했습니다. 이번에는 라이브러리 실행을 재검증하지 않았습니다. 외부 스크립트까지 포함한 안전 보증은 아닙니다. |
| 프론트 리스너 누수 | 확인한 소켓과 document 리스너에는 cleanup이 있습니다. 장시간 실행을 측정한 것은 아니며 서버 점수 캐시 수명 문제와는 별개입니다. |
| API 계약 | 이전 분석은 Axios 호출 39곳을 비교했고 탈퇴 API 누락을 확인했습니다. 요청 경로가 맞아도 응답 타입, 필드, 권한, 실제 성공 동작까지 맞는 것은 아닙니다. |
| 스케줄러 | ScheduleModule과 CleanupService 등록, cron 식이 존재합니다. 실제 실행 시각과 삭제 결과는 확인하지 않았습니다. |
| 비밀값 | 이전 분석은 서버 비밀값을 env에서 읽고, 과거 프론트 .env에는 공개 URL 두 개만 있었다고 기록했습니다. 이번 문서화에서 전체 Git 이력의 비밀값 검사를 다시 수행하지 않았습니다. |

## 검증 상태

| 구분 | 상태 |
| --- | --- |
| 이전 세션 기록 | 분석 결과와 Claude Docs 작성 도구 입력, 응답을 로컬 기록에서 복원 |
| 소스 기준 | 현재 HEAD가 기존 분석 기준과 같음을 확인 |
| 주요 근거 | 컨트롤러, 서비스, repository, 엔티티, 프론트 호출부, 설정을 대조 |
| 문서 | 상대 링크, 소스 줄 번호 범위, 표 항목 수와 Markdown 공백 확인 |
| 애플리케이션 빌드와 테스트 | 실행하지 않음 |
| DB와 브라우저 재현 | 실행하지 않음 |
| 배포 환경과 원격 Claude Docs | 현재 상태 미확인 |

실제 DDL과 인덱스, MySQL 세션 타임존, 외부 API 응답, 운영 환경 변수, 프록시와 다중 인스턴스 구성은 저장소만으로 확정할 수 없습니다. 조건부 항목은 이 자료와 격리 환경의 재현 결과를 얻은 뒤 결론을 갱신해야 합니다.
